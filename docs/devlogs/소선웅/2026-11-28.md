# 2026-11-28 개발 로그

- 작성자: 소선웅
- 작업 브랜치: `prototype/sunwoong`
- 근거: 사용자가 Windows 호스트·WSL·VM·웹에서 실행해 공유한 명령 출력과 화면. 건우/선웅의 연결 방식과 Python 버전은 다르며, 각 결과를 구분한다. 실제 IP·키·비밀번호는 기록하지 않는다.

## 공통 시험 환경

- Hyper-V Windows 11 VM `InstallONE-PC01`~`PC04`를 준비했다. 복제 원본은 Sysprep `/generalize /oobe /mode:vm /shutdown`으로 일반화했다. OS 볼륨 BitLocker가 켜져 있어 처음에는 `0x80310039`로 실패했고, 완전 복호화 후 진행했다. VM별 장치 이름·로컬 계정·동적 MAC을 분리하고 외부 스위치에 연결했다.
- 네 VM에서 WinRM/SSH 서비스를 확인했다. PC02~PC04의 복제된 SSH 호스트 키를 새로 생성하고, 호스트의 SSH 공개키 인증 및 WSL Ansible WinRM/NTLM `win_ping` 네 좌석 모두 성공했다.
- VM별 설치 전/후 Hyper-V 체크포인트를 만들었다. ‘설치 전’ 체크포인트에도 복제 원본 Python이 포함될 수 있으므로, 선웅 신규 설치 시험 전에는 네 VM에서 전용 Python 폴더와 해당 버전 제거 항목이 모두 없음을 따로 확인했다. 메인 호스트에는 설치 실험을 하지 않았다.

## 건우 프로토타입: WinRM·Ansible·Chocolatey

- WSL의 `InstallONE-geonwoo/development`에서 네 좌석의 WinRM 연결을 `pong`으로 확인했다. 앞선 PC01 단일 시험에서는 Python 3.12.10·pip 25.0.1 설치 및 예제 검증이 성공했다.
- 네 좌석 동시 웹 설치는 **4대 모두 Chocolatey `python312` 단계에서 실패**했다. VM의 `chocolatey.log`에서 확인한 최초 오류는 의존 패키지 `vcredist140`을 Chocolatey Community API에서 받을 때의 **HTTP 429 Too Many Requests**였다. 이어 `vcredist2015`와 `python312`가 선행 의존성 실패로 중단됐다. PC01 단독 재시도도 429였다.
- 네 좌석 **연결 성공과 설치 실패**를 구분한다. 이 로그만으로 Python 미지원이나 설치 코드의 일반적인 결함을 단정하지 않는다. 시험 후 VM을 설치 전 체크포인트로 복구했다.

## 선웅 프로토타입: SSH·공식 Python 설치

- 기존 1대 실설치 모드를 승인 좌석 1~4번(서로 다른 IPv4)으로 확장했다. `1번부터 4번 PC에 Python 실습환경 설치해 줘`의 규칙 해석, 한 작업의 최대 네 SSH 동시 실행, 완료한 좌석부터 SQLite 결과 저장을 구현했다. 확인 체크·최종 확인·VM 설정 지문 검사·기본 모의 모드는 유지했다. 사용자가 Windows 작업 폴더에 패치와 네 VM 설정을 적용했고, 첫 앱 테스트 **40개 통과**.
- 첫 네 좌석 웹 실행은 **기존 설치 재사용 4대 성공**이었다. 이를 신규 설치로 기록하지 않았다. 이후 네 VM의 InstallONE 전용 Python 3.14.7을 공식 제거하고 남은 전용 폴더를 점검해 정리했다. 네 VM 모두 전용 폴더 없음·해당 제거 항목 없음 확인 후 VM별 신규 설치 직전 체크포인트를 만들었다.
- 한 요청의 네 좌석 신규 설치 시험에서 PC01은 `새 설치; Python 3.14.7; 예제 출력 42 확인`으로 즉시 성공했다. PC02~PC04는 웹의 900초 SSH 응답 제한으로 `확인 필요`였지만, 네 VM 모두 전용 경로의 Python 3.14.7과 pip 26.2.1을 읽기 전용 SSH 점검으로 확인했다. **웹의 직접 신규 설치 완료 응답은 PC01만 받은 상태**라는 한계를 남긴다.
- 시간 초과 시 설치 명령을 반복하지 않고 독립적으로 Python 버전·예제 42·pip를 확인하는 검증을 추가했다. 이어 사전 검증 응답이 불명확해도 설치로 넘어가는 경로를 고쳐, **전용 경로 없음이 확인된 경우만** 설치하도록 했다. 응답이 늦은 좌석은 `확인 필요` 또는 사후 검증 성공으로 구분해 기록한다.

## SSH 지연 원인 분석과 최종 결과

- 동일한 읽기 전용 SSH 검증을 네 VM에 병렬로 반복했다. Python을 PowerShell 파이프로 실행해 **표준입력이 닫힌 상태**에서는 4대 × 5회 모두 약 0.8~1.4초에 `verified`. 열린 콘솔 표준입력을 상속한 `python -c`에서는 여러 VM이 반복해서 정확히 45초 후 `unknown`. 같은 코드의 SSH 자식 프로세스에 `stdin=subprocess.DEVNULL`만 적용한 대조 시험에서는 다시 **4대 × 5회 모두 약 0.8~1.4초에 성공**했다. `ssh -T`는 의사 터미널 할당만 끄며 표준입력을 닫지 않는다.
- 설치·사전 검증 SSH 두 호출에 닫힌 표준입력을 적용하고 회귀 테스트를 추가했다. Windows 앱 테스트 **45개 통과**. 처음에는 수정 파일이 있어도 구버전 서버 프로세스가 포트 5000을 계속 점유했다. 구버전 서버 종료·포트 해제·새 PID/시작 시각 확인 후 웹 시험을 다시 했다.
- **최종 웹 결과: 대상 4·처리 완료 4·실제 VM 성공 4·실패 0·확인 필요 0.** 네 좌석 모두 기존 설치 재사용, Python 3.14.7, 예제 출력 42, pip 확인. 이력 시작 16:13:11 KST, 16:13:24 화면에서 네 좌석 완료. 이는 앞서 설치된 네 VM의 **재사용 검증**이며, 수정을 적용한 뒤 네 VM을 재제거하고 신규 설치한 시험은 아니다.

## 비교 및 남은 일

| 항목 | 건우 프로토타입 | 선웅 프로토타입 |
|---|---|---|
| 원격 방식 | WSL Ansible → WinRM/NTLM, 4대 `pong` | Windows 호스트 → SSH 공개키, 4대 웹 검증 성공 |
| 설치 경로 | Chocolatey `python312`와 의존 패키지 | 공식 서명 Python 3.14.7 설치 파일, 계정 전용 폴더 |
| 4대 신규 설치 | `vcredist140` 다운로드 429로 4대 실패 | VM 4대에 Python·pip 존재 확인. 웹의 직접 신규 설치 완료 응답은 1대, 나머지는 사후 확인 |
| 최종 웹 검증 | 신규 설치 실패 후 4대 재시도 없음 | 표준입력 수정·서버 재시작 후 4대 재사용 검증 성공 |

- 공급 경로와 Python 버전이 달라 같은 조건의 속도·성능 우열로 해석하지 않는다. 건우 버전의 429 대응, 선웅 버전의 **표준입력 수정 후 4대 신규 설치 재시험**, SSH 중간 단절·설치 실패 복구 검증은 남았다. 실제 HaiGPT 호출 없이 모의 규칙 해석 + 실제 VM 설치 모드로 시험했다.
- 사용자 Windows 작업 폴더에서 코드 패치와 앱 45개 테스트를 확인했다. 이 로그가 작성된 별도 작업 환경에서는 변경이 미커밋이다. 비밀 `.env`·SSH 키·VM 파일은 버전 관리하지 않는다.
