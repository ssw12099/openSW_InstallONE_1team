# InstallONE 통합 개발 인수인계

작성: 소선웅 · 기준: 2026-11-28 KST · 브랜치: `prototype/sunwoong`

이 문서는 대화 이력이 없는 통합 담당자와 AI 개발 도구에 전달하기 위한 설명이다. 세 프로토타입 통합을 준비하며, 소선웅 구현과 사용자가 공유한 강건우 시험 결과를 정리했다. 세 번째 프로토타입의 코드·결과는 이 작업에서 검토하지 않았으므로 통합 담당자가 별도로 확인해야 한다. 실제 VM 테스트는 소선웅이 실행한다.

## 1. 무엇을 개발하는가

InstallONE은 한림대학교 오픈소스SW의 이해 1팀의 실습실 개발환경 설치 프로젝트다. 팀원은 소선웅·강건우·지재헌·신정빈이며, 개인 프로토타입을 비교해 통합하는 단계다. 저장소 일정은 12월 8일 1차 발표, 12월 15일 최종 발표다.

목표 사용자는 실습실 조교다. 조교가 브라우저에서 “1번부터 4번 PC에 Python 실습환경 설치해 줘”라고 요청하면, 시스템이 대상 좌석과 설치 프로필을 해석하고 확인 화면을 제시한다. 조교가 확인한 뒤 대상 Windows PC에 설치하고, 실제 실행 검증과 좌석별 결과·SQL 이력을 보여주는 흐름을 목표로 한다.

현재 선웅 구현의 핵심 범위는 자연어 요청 → 해석 → 허용 좌석·프로필 검증 → 사용자 확인 → 원격 설치/기존 설치 재사용 → 버전·예제·pip 검증 → 좌석별 결과·SQLite 이력이다. 현재 실제 지원 프로필은 Python 실습환경이다. 진단·FAQ·업데이트 등은 이 구현의 완성 기능으로 간주하지 않는다. 팀 전체 필수 기능의 최종 범위는 팀 문서와 세 프로토타입을 함께 확인해야 한다.

## 2. 선웅 프로토타입 구조와 통합 시 보존할 동작

| 영역 | 현재 구현과 읽을 파일 |
|---|---|
| 웹 | Flask + HTML/CSS/JavaScript. `development/app.py`, `templates/`, `static/` |
| 해석 | 모의 규칙 또는 HaiGPT. `installone/haigpt.py`, `settings.py` |
| 작업 관리 | 백그라운드 실행, 확인한 계획과 실행 모드 보존, 중복 실행 방지. `installone/web_jobs.py` |
| 업무·DB | 대상·프로필 재검증, SQLite 작업/좌석 결과 저장, 최대 4개 병렬 실행. `installone/core.py` |
| 실제 실행 | Windows 호스트에서 SSH 공개키 인증으로 Windows VM의 고정 PowerShell 절차 실행. `installone/executors.py`, `scripts/install_python.ps1` |
| 설치 방식 | 공식 서명 Python 설치 파일, 대상 계정의 `%LOCALAPPDATA%\InstallONE\Python314` 전용 경로. 전역 PATH 변경 없음 |
| 검증 | Python 버전, 예제 출력 42, pip. 새 설치와 기존 설치 재사용을 구분 |
| 설정 | 서버 로컬 `.env`, 공개 항목은 `.env.example`. 키·접속 설정·DB·가상환경은 Git 제외 |

해석 모드와 설치 모드는 별개다. 11월 28일 네 VM 시험은 **모의 규칙 해석 + 실제 VM 실행**이었다. 이 결과를 HaiGPT까지 포함한 네 VM 종단간 시험으로 기록하면 안 된다. 과거 실제 HaiGPT 해석 시험은 별도 이력이 있으나 통합판에서도 다시 검증해야 한다.

AI가 만든 문자열을 그대로 명령으로 실행하지 않는다. 허용된 좌석과 설치 프로필로 검증하고, 고정 설치 절차에 연결한다. 실행 직전 대상·설치 범위를 확인하며, 확인 후 VM 설정이 바뀌면 기존 확인 요청을 재사용하지 않는다. 한 좌석이 실패하더라도 다른 좌석 결과를 보존한다. 응답 시간 초과는 성공이나 확정 실패로 단정하지 않고 `확인 필요`로 구분한다.

현재 서버는 localhost의 개발용 운영 형태다. 실습실 여러 조교가 접속하는 중앙 서비스의 사용자 인증·권한·배포·운영이 검증된 상태는 아니다.

## 3. 두 프로토타입의 시험 결과

| 항목 | 건우 | 선웅 |
|---|---|---|
| 원격 경로 | WSL → Ansible → WinRM/NTLM | Windows 호스트 → SSH 공개키 → PowerShell |
| 설치 공급 경로 | Chocolatey `python312` 및 의존 패키지 | 공식 Python 설치 파일 |
| 시험 버전 | Python 3.12.10, 단일 성공 시 pip 25.0.1 | Python 3.14.7, VM 점검 시 pip 26.2.1 |
| 연결 | 4대 모두 `win_ping`의 `pong` 확인 | 4대 SSH 접속 및 최종 웹 검증 확인 |
| 단일 설치 | PC01 설치·예제 검증 성공 | 신규 설치·재사용 경로 시험 |
| 4대 신규 설치 | 의존 패키지 다운로드 429로 4대 실패 | PC01 직접 완료 응답. PC02~04는 초기 시간 초과 후 별도 점검에서 Python·pip 확인 |
| 최종 웹 결과 | 429 해결 후 4대 재시험 기록 없음 | SSH 수정 및 서버 재시작 후 4대 재사용 검증 성공, 실패/확인 필요 0 |

버전과 설치 공급 경로가 다르므로 같은 조건의 성능 비교로 해석하지 않는다. 세 번째 프로토타입의 장단점·테스트 상태는 아직 이 문서의 근거 범위 밖이다.

## 4. 발생한 문제와 확인한 원인

### Chocolatey 다운로드 제한

건우의 네 VM 설치 로그에서 `vcredist140` 다운로드가 HTTP 429 Too Many Requests로 실패했다. 이후 `vcredist2015`, `python312`가 의존성 실패로 중단됐고 PC01 단독 재시도도 429였다. 네 VM 연결 자체는 성공했다. 제한의 정확한 정책·해제 시간은 확인하지 않았다.

통합 시 다운로드 재시도 간격, 공급 경로, 검증된 설치 파일 캐시 및 동시 다운로드 수를 설계해야 한다. 무조건 즉시 재시도하거나 의존성을 무시하는 방식으로 해결하지 않는다. 캐시를 채택한다면 버전·출처·서명 검증도 함께 관리해야 한다.

### 설치는 됐는데 웹은 오래 기다리는 SSH 문제

선웅의 초기 네 VM 시험에서 실제 Python·pip가 존재해도 웹은 최대 900초 기다리거나 완료 불명으로 끝났다. 지연 좌석은 매번 같지 않았다.

동일 검증을 반복한 대조 시험에서 다음 차이가 나타났다.

- PowerShell 파이프로 Python을 실행해 입력이 닫힌 조건: 4대 × 5회 모두 약 0.8~1.4초에 `verified`.
- 콘솔에서 `python -c`로 실행해 열린 표준입력을 상속한 조건: 여러 좌석이 45초 제한에 걸려 `unknown`.
- SSH 자식 프로세스에 `stdin=subprocess.DEVNULL`을 적용한 조건: 4대 × 5회 다시 약 0.8~1.4초에 `verified`.

이 대조 시험은 SSH의 호스트 표준입력 상속이 지연을 유발한 원인이라는 근거다. 설치·사전 검증 두 SSH 호출에 DEVNULL을 적용했다. `ssh -T`만으로 표준입력이 닫히는 것은 아니다. 통합 후에도 실제 서버 실행 방식에서 이 조건을 유지해야 한다.

시간 초과 후 별도 검증하는 보완도 추가했다. 사전 검증이 불명확하면 설치로 넘어가지 않으며, 전용 경로가 없다고 확인된 경우에만 설치한다. 단순히 제한 시간을 늘리는 것만으로 해결된 문제라고 기록하지 않는다.

### 수정한 파일과 실행 중 서버가 달랐음

패치를 적용하고 테스트 45개가 통과했어도 이전 서버가 포트 5000을 점유한 채 실행되고 있었다. 포트 점유 PID와 시작 시각을 확인해 구버전 서버를 종료하고 새 서버로 바꾼 뒤, 16:13 KST 웹 시험에서 4대 모두 재사용 검증이 성공했다.

통합판에는 실행 중 빌드/커밋 버전과 서버 시작 시각을 확인할 수 있는 운영 정보를 두는 것이 좋다. 테스트 결과만으로 실행 중 서비스에 수정이 반영됐다고 판단하지 않는다.

### 핵심 요구사항: HaiGPT가 조교의 자유로운 표현을 분석해야 함

소선웅의 추가 요구: 조교가 정해진 문장을 외워 입력해야 한다면 LLM을 사용하는 목적이 충족되지 않는다. HaiGPT는 조교의 자연어에서 대상 좌석, 설치할 환경, 제외 조건을 추출해 구조화된 설치 계획을 만들어야 한다. “1번부터 4번”을 “1~4번”으로 바꾸었다고 같은 의미의 요청이 거절되는 동작은 통합판에서 해결해야 할 핵심 사용성 문제다.

이번에 “1~4번 Python 실습환경 요청”을 거절한 화면은 **모의 규칙 해석 모드**였다. 따라서 이 사례를 실제 HaiGPT의 해석 실패라고 단정하지 않는다. 다만 실사용 기본 흐름을 모의 규칙에 머물게 하거나, 실제 LLM을 호출하기 전에 고정 문구 검사로 정상적인 자연어를 차단하면 같은 문제가 남는다. 통합 담당자는 실제 호출 경로와 화면의 모드 표시부터 확인해야 한다.

권장 처리 흐름은 `자유로운 요청 → HaiGPT 의미 분석 → 구조화된 좌석·프로필 계획 → 서버 검증 → 조교 확인 → 고정 설치 절차`다. 입력 문구의 다양성은 허용하면서 실행 대상과 설치 종류는 등록된 범위로 제한한다. LLM은 설치 명령을 자유롭게 생성·실행하는 역할을 맡지 않는다.

통합판의 실제 HaiGPT 검수에는 다음 사례를 포함한다. 아래는 구현 완료 보고가 아니라 통합 시 충족할 요구사항이다.

| 요청 예시 | 기대 동작 |
|---|---|
| “1번부터 4번 PC에 Python 실습환경 설치해 줘” | 좌석 1·2·3·4, Python 프로필 |
| “1~4번 Python 실습환경 요청” / “1-4번에 파이썬 깔아줘” | 위와 같은 계획으로 해석 |
| “1, 2, 3, 4번 컴퓨터 파이썬 준비해 줘” | 위와 같은 계획으로 해석 |
| “전체 PC에 파이썬 설치해 줘” | 선택된 실습실의 등록 좌석을 명시해 확인. 실습실 범위가 없으면 질문 |
| “1~4번 중 2번 빼고 파이썬 설치해 줘” | 좌석 1·3·4로 해석하고 제외 결과를 표시 |
| “저쪽 컴퓨터에 설치해 줘” | 대상·환경 등 빠진 정보를 질문. 임의 실행하지 않음 |
| 등록되지 않은 좌석 또는 지원하지 않는 설치 환경 | 지원 범위를 설명하고 요청 보완 안내. 다른 대상으로 임의 대체하지 않음 |

표현이 다르다는 이유로 거부하는 경우와 실제로 뜻이 불명확한 경우를 구별해야 한다. 해석 실패 시 정해진 문구로 다시 쓰라고만 안내하기보다 필요한 정보를 질문하는 방향이 적합하다. 실제 HaiGPT 시험은 소선웅이 연결 설정을 갖춘 환경에서 수행하며, 모의 응답 테스트와 결과를 따로 기록한다.

### 요청 문구와 상태 안내의 한계

모의 해석에서 “1~4번 Python 실습환경 요청”이 거부된 사례가 있다. 지원 문구를 이용하면 통과하지만, 자연어 해석의 허용 범위와 오류 안내 개선이 필요하다. 진행 중 화면의 “작업을 기다리고 있습니다”는 연결·다운로드·설치·검증 중 어디에서 멈췄는지 설명하지 못했다. 단계, 경과 시간, 제한 시간, 재시도 가능 여부를 보여줄 필요가 있다.

## 5. 가장 큰 실사용 과제: 조교가 대상 PC를 연결하기 너무 어려움

소선웅의 사용자 관점 판단: 현재 연결 준비 과정은 개발자와 관리자가 직접 명령을 입력하며 해결하는 수준이다. 일반 조교가 실습실에서 바로 사용할 수 있다고 보기 어렵다. 웹 설치 기능이 성공해도 대상 PC 등록 과정이 그대로라면 실제 사용의 진입 장벽이 크다.

이번 시험에는 VM 생성·복제, 네트워크 스위치/IP 확인, 로컬 계정, WinRM 또는 SSH 서비스, 방화벽 프로필, 공개키 등록, 호스트 키 확인, 좌석 매핑 등이 필요했다. 특히 PC02는 네트워크가 Public인데 SSH 허용 규칙은 Private에만 적용돼 접속이 지연됐다. PC01은 WinRM 서비스가 꺼져 있었고, Default Switch에서 외부 스위치로 연결을 바꿔야 했다. 복제 후 SSH 호스트 키도 VM별로 분리했다.

통합판에서는 다음 사용자 경험을 먼저 설계할 것을 제안한다.

1. **초기 관리자 준비와 매 수업 조교 작업을 분리한다.** 서비스·방화벽·권한 준비는 실습실 관리자가 한 번 수행하고, 조교는 등록된 실습실·좌석을 선택하게 한다.
2. **대상 등록/연결 점검 화면을 만든다.** 실습실과 좌석별 PC를 등록하고, 연결·인증·권한·설치 가능 상태를 점검한다. “연결 실패” 대신 관리자 조치가 필요한 이유를 알려준다.
3. **반복 가능한 초기 설정을 제공한다.** 승인된 초기 설정 도구, 기관의 기존 일괄 관리 방식, 대상 PC의 등록 에이전트 중 무엇이 가능한지 학교 환경을 확인해 선택한다. 아직 채택된 기술 결정은 아니다.
4. **주소 변경과 중복 등록을 다룬다.** 현재 IP 기반 등록을 실제 환경에서 유지할 수 있는지 확인하고, 좌석과 PC 식별이 어긋난 경우 실행을 막는다. 네트워크에서 발견됐다는 이유만으로 설치 대상으로 승인하지 않는다.
5. **최소 권한과 유지관리 책임을 명확히 한다.** 자격 증명 관리, 키 교체, 대상 해제, 연결 복구의 담당자와 절차를 정한다. 실습실 전체 방화벽을 끄거나 무제한 원격 접근을 허용하는 해결책은 사용하지 않는다.

초기 설정 에이전트나 별도 서비스 도입은 설치 난이도를 줄일 수 있지만 배포·업데이트 부담도 생긴다. 통합 담당자는 학교 PC의 관리자 권한, 도메인/관리 정책, 네트워크 제약을 확인한 뒤 결정해야 한다.

## 6. 실제 VM 환경과 인수인계 상태

아래는 마지막으로 공유된 사용자 실행 결과 기준이며, 통합판 테스트 전에 현재 상태를 다시 확인한다. 실제 IP·비밀번호·키 내용은 공개 문서에 포함하지 않는다.

| 항목 | 확인된 환경 |
|---|---|
| 테스트 담당 | 소선웅이 집 Windows 호스트에서 직접 실행 |
| 가상화 | Hyper-V, Windows 11 VM 네 대 |
| VM 이름 | `InstallONE-PC01`, `InstallONE-PC02`, `InstallONE-PC03`, `InstallONE-PC04` |
| 좌석 | 1~4번을 PC01~04에 각각 매핑 |
| 네트워크 | 네 VM 모두 `InstallONE-External` 외부 스위치 연결 확인. 호스트·VM 같은 LAN 구성 |
| 자원 | 공유된 점검 시 VM당 메모리 6 GiB, 네 대 Running. 이 수치는 권장 최소 사양으로 검증한 값은 아님 |
| 계정/접속 | 대상 로컬 계정으로 SSH 공개키 인증, 별도 WSL에서 WinRM/NTLM 시험 |
| 현재 설치 상태 | 마지막 성공 화면 기준 4대 모두 계정 전용 Python 3.14.7 존재·예제 42·pip 검증 성공 |
| 선웅 실행 위치 | 호스트의 `InstallONE-git/development`, Windows `.venv`, localhost:5000 |
| 건우 실행 위치 | WSL의 `InstallONE-geonwoo/development`, 별도 환경·설정 |

체크포인트는 VM별로 존재한다. 이름의 PC 번호를 실제 VM과 맞춰 사용한다.

- `PC0N - WinRM SSH 연결 완료 - 설치 전` 계열: 초기 연결 준비 상태. PC01은 `4대 설치 전` 이름이다. 이 이름만으로 Python 부재를 보장하지 않는다.
- `PC0N - 선웅 재사용 검증 성공 - Python 설치됨`: 기존 설치 재사용 검증 후 보관한 상태.
- `PC0N - 선웅 신규 설치 직전 - Python 없음`: 공식 제거 및 남은 전용 폴더 정리 후, 네 VM 모두 전용 폴더와 해당 제거 항목이 없음을 확인하고 생성한 상태.

현재 VM은 신규 설치 직전 체크포인트가 아니라 그 이후 설치된 상태다. 기존 Python이 있는 상태에서 성공하면 “신규 설치 성공”으로 집계하지 않는다. 체크포인트 복구 후에는 서비스·방화벽·키·IP가 과거 상태로 돌아갈 수 있으므로 연결과 대상 매핑을 다시 확인해야 한다. 이전 복구에서는 VM이 Saved 상태로 나타났고 저장 상태 제거 후 시작했다. 저장 상태 제거는 메모리 실행 상태를 버리므로 일반적인 필수 절차로 자동화하지 않는다.

VM 복제 과정에서는 Sysprep 일반화와 SSH 호스트 키 분리를 수행했다. BitLocker 때문에 Sysprep이 실패한 이력이 있으나, 이는 시험 VM 준비 과정의 문제이며 조교가 매번 수행해야 할 앱 사용 절차가 아니다.

## 7. 통합판을 넘길 때와 소선웅이 테스트할 순서

통합 담당자는 테스트할 커밋, 변경 범위, 실행 명령, 설정 예시, 예상 결과와 로그 위치를 함께 제공한다. 비밀 설정은 소선웅의 로컬 환경에서 적용한다. AI 도구나 다른 개발자가 실제 VM 시험을 수행했다고 기록하지 않는다.

1. 실행 중 서버를 확인하고 테스트할 코드의 새 서버를 시작한다. 네 좌석 매핑·VM 연결·현재 Python 유무를 읽기 전용으로 확인한다.
2. 현재 설치 상태에서 **4대 재사용** 시험을 한다. 네 좌석 모두 버전·42·pip 결과와 새 설치/재사용 구분이 맞는지 확인한다.
3. 소선웅이 준비한 Python 없는 상태로 복구하고 실제 부재를 확인한 뒤 **4대 신규 설치**를 시험한다. 설치 전 대상과 범위를 확인하며, 호스트에는 설치 실험을 하지 않는다.
4. 신규 설치가 끝난 동일 상태로 다시 요청해 재사용 동작과 중복 실행 방지를 확인한다.
5. 한 좌석의 연결 실패, 다운로드 실패, 응답 제한, 서버 재시작을 통제된 조건에서 시험한다. 다른 좌석 결과가 보존되는지, 완료 불명에서 중복 설치를 유발하지 않는지 확인한다.
6. 각 시험의 커밋·시각·초기 상태·좌석별 단계/시간·최종 검증 결과를 남긴다. 전체 완료율 100%와 설치 성공률 100%를 구별한다.

45개 자동 테스트 통과는 실제 VM 네트워크·설치 성공의 대체 증거가 아니다. 최종 DEVNULL 수정 후 **4대 신규 설치 전체 흐름은 아직 재시험하지 않았다.** 최종 확인된 것은 네 대 재사용 웹 검증이다. 이 남은 시험을 통합판의 우선 검증 항목으로 둔다.

## 8. 통합 개발의 권장 우선순위

- 세 프로토타입을 같은 기준으로 읽고, 기반 코드와 가져올 기능을 결정한다. 세 개의 웹 서버·설정 로더·DB 모델을 그대로 겹쳐 붙이지 않는다.
- 좌석/PC 등록, 설치 프로필, 작업과 좌석별 상태, 실행 결과를 공통 계약으로 정한다. SSH와 WinRM 중 선택하거나 실행기를 분리하더라도 웹의 상태 의미는 같아야 한다.
- 대상 연결 준비의 사용성, 비밀 설정 관리, 실패 원인 표시를 핵심 기능과 함께 다룬다.
- 네 대 신규 설치·재사용·실패 복구를 같은 조건에서 검증한 뒤 실습실 확대 여부를 판단한다. 현재 시험을 실제 학교 다수 PC 운영 검증으로 확대 해석하지 않는다.
